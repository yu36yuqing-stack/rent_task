# Production Release

按照项目既有发布流程完成生产发布，并给出可审计的结果报告。发布动作必须继续由 `scripts/merge_code.sh` 执行，本 Skill 负责授权检查、发布前检查、结果核验和失败处理。

## 授权边界

- 仅当当前请求或正在继续的同一次发布任务中存在用户明确的“发布生产”或“发布宿主机”授权时执行。
- 用户只要求方案、落地代码、测试、提交、推送或合并时，不得执行生产发布。
- 用户要求查看或 Review 发布流程时，只读取本 Skill、检查清单和脚本，不运行脚本。
- 本 Skill 的加载不等于发布授权；实际运行脚本前必须再次核对上述触发条件。

## 执行流程

1. 阅读根目录 `AGENTS.md`、`config/codex_rule.md` 和 [发布检查清单](references/release-checklist.md)。
2. 从项目根目录检查当前分支、工作区差异和待发布范围：
   - 区分源代码/文档改动与 `database/*.db`、`log/` 等运行态变化。
   - 确认所有会被同步并提交的文件都属于本次发布。
   - 因脚本会执行本机代码对齐，确认重要未提交代码已提交、已备份或确实包含在本次发布中。
   - 若待发布范围不明确或可能丢失代码，在运行脚本前停止并向用户说明。
3. 检查本次变更对应的测试、覆盖率和迁移：
   - 已有有效测试结果可以复用；结果过期或代码之后又变化时重新执行。
   - 代码变更按 `AGENTS.md` 要求运行定向测试和必要回归测试。
   - 仅文档或 Skill 变更无需运行无关业务测试，但要执行格式和结构校验。
   - 发现未验证的迁移、高风险失败或阻塞性测试失败时，不进入生产发布。
4. 不修改脚本内容，直接从项目根目录执行：

   ```bash
   bash scripts/merge_code.sh
   ```

5. 按脚本输出逐项确认五个阶段，不得只根据退出码概括成功：
   - 代码同步至宿主机。
   - 宿主机提交并推送目标分支。
   - 数据库迁移、服务重启和 `/api/ping` 健康检查。
   - 本机代码与远程仓库目标分支对齐。
   - 生产数据库和日志回拉到本机。
6. 发布后核对本机提交、分支、工作区状态，以及数据库和日志同步结果。不得把数据库回拉产生的运行态修改误报为代码未提交。
7. 按检查清单中的格式向用户提交发布报告。

## 失败处理

- 任一步失败立即记录失败阶段、错误摘要、已经完成的阶段和当前环境状态。
- 不得因为后续本机同步失败，就错误地判断生产一定没有发布；应明确生产代码、服务、仓库和本机分别处于什么状态。
- 不自动重复执行完整发布脚本，避免重复提交、重复迁移或覆盖现场。
- 不手工跳过失败步骤继续执行，也不擅自回滚、改生产数据或修改发布脚本。
- 只有在失败原因明确、重复执行无副作用且仍有用户发布授权时，才可重试；否则先把恢复方案交给用户 Review。

## 安全约束

- 不在输出、报告、Skill 或新增代码中记录密码、令牌和完整凭据。
- 不把生产数据库、日志或敏感配置提交到代码仓库。
- 测试和发布前检查不得调用额外的生产写接口。
- 不以 Skill 或子 Agent 替代用户的生产发布授权。
