# AGENTS.md - rent_task/h5

本文件适用于 `h5/` 目录及其全部子目录，并在根目录 `AGENTS.md` 和 `config/codex_rule.md` 基础上补充 H5 专项规则。

## 1. 修改前置条件

- 任何 H5 代码、结构、样式或交互修改，都必须先按根目录 `AGENTS.md` 完成方案 Review，并取得用户明确的落地批准。
- 方案设计前必须阅读 `h5/COMPONENT_GUIDE.md`，并搜索 `h5/public/index.html`、`h5/public/css/app.css`、`h5/public/js/` 中的已有实现。
- 方案必须包含组件复用清单，逐项说明：需求元素、已有组件、复用决策、影响页面和验证方式。
- 不得仅根据组件指南判断实现情况；指南是注册表，实际契约仍需与 HTML、CSS、JS 和测试交叉验证。

## 2. 公共组件强制规则

1. 相同业务语义必须使用相同的 DOM 结构、基础 CSS 类和公共 JS 行为，不得在新页面复制一套同义实现。
2. 游戏是组件的数据输入，不是组件分叉条件。CS2、和平精英、王者荣耀、CFM 等游戏必须复用同一套组件，只允许通过 `game_id`、名称、图标、状态、配置或插槽表达差异。
3. 仅当游戏之间存在已确认的真实业务或交互差异时，才允许增加变体；不得仅因游戏名称不同创建专属组件或专属样式。
4. 复用优先级固定为：直接复用稳定组件 -> 扩展已有组件变体 -> 新建公共组件 -> 页面专属实现。
5. 同一结构或交互出现第二个使用页面或第二个游戏时，必须优先提升为公共组件，不允许继续复制。若本次暂不抽取，必须在方案中说明原因并取得用户确认。
6. 新增可复用 JS 组件统一放入 `h5/public/js/ui/`；在首次新增前，不要求为满足目录形式而重构既有页面代码。
7. 当前公共 CSS 仍以 `h5/public/css/app.css` 为事实来源。公共组件样式必须使用独立基础类，不得依赖具体页面 ID 才能生效。
8. 页面 ID 选择器只允许承载页面布局或经确认的页面变体，不得用于复制、覆盖公共组件的完整视觉定义。
9. 禁止新增内联 `style`。颜色、字号、间距、圆角、阴影等应优先使用已有设计 Token 和公共组件基线。
10. 不为相同语义创建新的同义类名；新增命名前必须搜索现有类和组件注册表。

## 3. 组件积累规则

- `h5/COMPONENT_GUIDE.md` 是组件注册表。只有登记了组件名称、状态、契约、使用方、变体和验证方式的实现，才算正式公共组件。
- 新组件初始状态为“试用”；在至少两个页面或两个游戏场景复用，并完成跨使用方验证后，才能标记为“稳定”。
- 试用组件可以继续完善，但新调用方不得复制实现；应复用或先完成公共化。
- 页面变体必须基于稳定公共组件，只记录差异，不复制基础组件完整规则。
- 废弃组件必须先标记为“废弃”，记录替代组件和迁移范围；不得直接删除仍有调用方的组件。
- 每次新增或修改组件，必须在同一次改动中更新组件注册表。文档与实现不一致时，任务不得交付。

## 4. 新页面准入规则

新页面方案至少检查并优先复用以下组件类别：

- 页面容器和布局。
- 游戏页签、主筛选、快捷筛选和汇总文本。
- 页面级按钮、卡片级按钮和危险操作按钮。
- 列表卡片、状态标签、空状态和分页。
- Sheet、Overlay、Toast 和 Loading。
- 游戏头像、名称和游戏身份展示。

如现有组件不能满足需求，方案中必须明确是增加变体还是新建组件，并说明为什么不能复用已有契约。

## 5. 验证与交付

- 修改稳定公共组件时，必须列出并验证注册表中的全部使用方，不能只检查当前页面或当前游戏。
- 新增或实质修改公共 JS 组件时，相关核心文件行覆盖率必须达到 90% 以上，并覆盖正常、边界、异常和状态切换。
- 视觉组件至少验证手机和桌面视口；多游戏组件至少验证不同名称长度、缺失图标、横向溢出、激活态和空数据。
- 新页面必须验证所有支持游戏使用同一组件契约，不能只验证默认游戏。
- 完成 H5 代码修改后，按 `config/codex_rule.md` 重启本地 H5、检查 `/api/ping`，并在测试报告中列出组件复用情况和全部受影响页面。
- 仅更新规则或组件文档、不改 H5 运行代码时，无需启动服务和执行无关业务测试，但必须进行 Markdown 和差异检查。
