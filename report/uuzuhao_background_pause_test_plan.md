# 悠悠授权异常后台暂停：改动与测试方案

日期：2026-09-09。范围：本地实现与隔离测试，未发布生产，未调用真实渠道接口进行验证。

## 行为边界

授权异常按 `uid + game_id + game_account + uuzuhao` 隔离，识别 `ACCOUNT_ERROR`、`AUTHORIZE_ERROR`、`REAUTHORIZE_ERROR`。

| 操作 | 授权异常时 |
| --- | --- |
| 商品同步、订单同步、订单详情 | 保持原有调用 |
| 自动或手工商品上架、下架 | 不加入后台授权暂停拦截；保留租赁、黑名单、渠道限制等原有判断 |
| 后台在线查询、禁玩查询、开启或解除禁玩 | 本地拦截，不发送渠道请求 |
| 自动解除授权和失败重试 | 原任务等待授权恢复，不计作新失败 |
| 手工在线、禁玩、令牌码操作 | 正常请求，展示真实接口结果 |
| 手工解除授权 | 合并现有任务并允许一次主动尝试；仍需等待在租订单结束 |
| 自动释放黑名单的前置查询 | 授权异常时不查询，不得因未知结果清除保护 |

商品同步确认恢复后，下一轮自动处理继续检查当前条件。不新增 `gameId=3` 排除。昨日人工取消的任务不在本次修改中自动恢复。

## 改动清单

| 文件 | 修改内容 |
| --- | --- |
| `product/prod_channel_status.js` | 增加 ACCOUNT_ERROR 统一识别及展示原因 |
| `product/prod_probe_cache_service.js` | 统一后台检查，手工调用显式放行；在缓存命中前检查；数据库读取失败不再默认放行 |
| `product/prod_status_guard.js` | 风控任务保留 pending/watching 阶段，延后本地检查，不计失败、不忽略风险事件；覆盖执行中状态发生变化的情形 |
| `order/auth_revoke_task_service.js` | 等待授权恢复、手工一次尝试、任务详情文案；保留在租订单保护 |
| `database/runtime_task_db.js` | 复用已有手工附着计数，JSON 记录已消费次数；原子保留执行期间的新触发记录；队列按是否首次执行和上次检查时间排序，避免等待任务饥饿阻塞其他任务 |
| `blacklist/blacklist_release_guard.js` | 传递手工上下文；查询失败或授权暂停时返回无法验证，不再用默认 false 清除保护 |
| `blacklist/blacklist_manual_remove_v2.js` | 手工前置查询显式放行并携带完整游戏身份 |
| `action_engine/action_engine.js` | 已识别的悠悠账号授权异常不因通用异常状态禁止补上架；其他渠道/异常类型规则不变 |
| `h5/local_h5_server.js` | 移除手工查询授权预拦截；手工查询实际刷新，继续映射上游错误 |
| `h5/public/js/menu_products.js` | 等待时卡片短标签“待授权”，点击显示完整原因；轮询结束提示保留实际失败信息 |
| `report/dingding/ding_style.js` | 现有汇报中增加需号主重新授权的清单，不逐次失败发送通知，不同时显示“所有状态正常” |

不新增数据库表或列。`manual_consumed_count` 使用现有任务 `result_json`；不修改订单结构。手工触发次数与执行结果在数据库更新时合并，避免异步请求期间新触发的记录被旧快照覆盖。

## 测试矩阵

| 场景 | 验收断言 |
| --- | --- |
| 三种授权异常 | 四类后台探测/禁玩操作的渠道请求数均为零 |
| 缓存仍有效 | 后台不能因缓存命中绕过暂停；不写入虚假的离线或未禁玩结果 |
| 用户、游戏隔离 | 同账号不同 uid、不同游戏正常查询 |
| 数据库查询失败 | 异常向上返回，不能默认允许后台请求 |
| 自动解除授权重复调度 | 同一任务保持等待，attempt_count 不变，请求数为零 |
| 手工覆盖后台等待 | 同一 task_id 真正尝试一次，失败结果保存，随后后台不再持续请求 |
| 请求执行中再次点击或订单结束 | 保留新增 triggers，只调用一次，手工额度正确消费 |
| 授权恢复后出现新租赁订单 | 等待在租订单结束后才解除授权 |
| 队列限额为 1 | 正常账号不被旧的等待任务挡住；CFM gameId=3 仍可执行 |
| 风控任务暂停与恢复 | pending/watching 阶段、风险事件保留；在线查询/开启禁玩/解除禁玩过程中发现异常也不消耗重试次数；恢复后正常结束 |
| 黑名单释放 | 后台暂停保留原禁玩保护；手工前置查询仍调用接口 |
| 手工 H5 接口 | 在线、禁玩查询/设置、令牌码、结束维护、移出黑名单均到达模拟接口，展示真实结果而非本地授权预拦截 |
| 上下架与同步 | 上下架、订单列表/详情仍调用 API；授权异常不新增上架暂停规则；其他渠道动作回归 |
| 页面及通知 | “待授权”短标签、完整错误详情、轮询提示正确；汇报提示号主且不误报全部正常 |

12 个测试入口组成回归套件。数据写入临时目录，外部 API 使用 fetch mock 或已有依赖替身；H5 使用临时数据库和本地测试端口，禁用测试环境风控定时器。

## 覆盖率口径与结果

- 验收口径：本次新增、修改的业务可执行行，不是整个历史仓库覆盖率。
- 使用改动前的工作区快照计算差异，不以 HEAD 为基准，避免把已有未提交改动算入本次范围。
- c8 收集实际执行数据，Istanbul 行覆盖数据与差异行求交集；11 个业务文件全部纳入，未加载文件也纳入收集。
- 实测：12/12 测试入口通过；改动行覆盖 **123/123，100%**，门槛 **90%**。
- 同一套测试对这些完整历史文件的总体行覆盖约 40.95%，不声称全文件或全仓库达到 90%。行覆盖也不等于所有分支覆盖。
- 改动行清单及文件哈希保存在 `test/fixtures/uuzuhao_background_pause_changed_lines.json`，源码变化使哈希不匹配时验证失败，防止旧清单继续报达标。

运行：

```sh
npm run test:uuzuhao-background-pause
npm run coverage:uuzuhao-background-pause
```

第二条命令同时运行测试、生成覆盖率报告并校验 90% 门槛，低于门槛返回非零退出码。

报告：`coverage/uuzuhao-background-pause/index.html`、`coverage/uuzuhao-background-pause/changed-lines.json`。

重新确定改动范围时，必须用真实的改动前源码目录重新生成清单，不能仅为过测试调整行号：

```sh
node test/check_uuzuhao_background_pause_coverage.js /path/to/pre-edit-source
```
